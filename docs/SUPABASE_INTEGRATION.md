# Supabase integration checklist

Everything in this branch runs without Supabase (`STORAGE_DRIVER=memory`, the default outside production). This list covers what to verify and change once someone has Dashboard access.

## 1. Storage (S3 API): confirmed and verified

The team confirmed the settings on 2026-11-21: endpoint `https://<project-ref>.storage.supabase.co/storage/v1/s3`, region `ap-southeast-1`, bucket `aura-farmer-bucket`.

- **Read-only check:** the app's `S3Storage.check()` succeeded with those settings.
- **One write round trip:** with approval, `scripts/s3-upload-smoke.ts` uploaded a synthetic PDF, read it back byte for byte, and deleted it.
- **The earlier `SignatureDoesNotMatch`:** caused by a wrong region (`ap-southeast-2`) in a local env file. A wrong bucket name would have failed next. Both now produce clear `storage_config` messages.

Outside production, S3 needs `ALLOW_DEV_S3=1` (see `docs/LOCAL_SETUP.md`).

## 2. What to verify in the Dashboard

- [ ] **Settings → General**: project region. Expected `ap-southeast-1` (Singapore).
- [ ] **Storage → Buckets**: decide whether resumes go in `aura-farmer-bucket` or in a dedicated private `resumes` bucket. Recommended: a dedicated bucket, **Private**, file size limit 5 MB, allowed MIME types `application/pdf` and `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.
- [ ] **Storage → S3 Connection**: endpoint, region, and an access key pair *for this environment*. S3 keys **bypass RLS** and have full storage access, so they are server-only and must never get a `NEXT_PUBLIC_` prefix.
- [ ] **Authentication → URL configuration**: site URL and redirect URLs include `http://localhost:3000` and the deploy URL. The team's OAuth and confirm routes depend on these.

## 3. Choose the upload path

| Option | Status | Notes |
|---|---|---|
| **A. S3 keys on the server** | Implemented (`S3Storage`) | Works today once the env vars are correct. The server enforces per-user keys (`<userId>/resumes/<uuid>.<ext>`), not RLS. |
| **B. supabase-js with the user's session** | Not yet implemented | RLS applies, so the database itself enforces per-user access. Recommended for production. Add a `SupabaseStorage implements ObjectStorage` that uses `createClient()` from `~/lib/supabase/server`. Nothing else changes. |

Storage policies for option B (bucket `resumes`; the first path segment is the user id, which `resumeKey()` already produces):

```sql
create policy "resume insert own" on storage.objects for insert to authenticated
  with check (bucket_id = 'resumes' and (storage.foldername(name))[1] = (select auth.uid())::text);
create policy "resume select own" on storage.objects for select to authenticated
  using (bucket_id = 'resumes' and (storage.foldername(name))[1] = (select auth.uid())::text);
create policy "resume delete own" on storage.objects for delete to authenticated
  using (bucket_id = 'resumes' and (storage.foldername(name))[1] = (select auth.uid())::text);
```

## 5. Database

The schema is ready and tested, but **not applied anywhere**:

1. `drizzle/0000_apply_workflow.sql` (generated by drizzle-kit from `src/server/db/apply-schema.ts`) creates `aura-farmer_resume`, `_candidate_profile`, `_application`, `_apply_job` and `_apply_job_log`. It also includes the team's existing example table, `aura-farmer_post`.
2. `supabase/apply-policies.sql` adds foreign keys to `auth.users` with on-delete cascade, enables RLS, and creates select-own policies. There are no client write policies, because all writes go through the server.

Both are verified on PGlite in `tests/repos/rls.test.ts`, using a test-only stand-in for the `auth` schema. Apply them in this order once there's access, ideally to a branch or staging project first.

## 6. Middleware behaviour

`src/lib/supabase/middleware.ts` (team code, unchanged) redirects anonymous `/api/*` calls to `/auth/login` instead of letting the route return 401. Our client helper (`src/lib/client/api.ts`) detects this and shows "Your session expired", covered by an end-to-end test. It would still be cleaner for API routes to receive a JSON 401. That's the team's decision: the change is to skip the redirect for paths starting with `/api/`.

## 7. Integration tests to run once access is granted

1. Run a read-only `ListObjectsV2` on the chosen bucket with the corrected env.
2. Apply the migration and policies to a staging project. Then run `REPO_DRIVER=postgres DATABASE_URL=<staging> pnpm test` against it; the repository contract suite is driver-agnostic and can be pointed at it.
3. Sign up a real test user. Upload a synthetic resume on `/apply/profile` and check that the `<uid>/resumes/` object and the database rows exist.
4. Start the worker against staging (`pnpm worker`) and run a test-form application end to end.
5. With a second user, confirm `/apply/applications/<first user's id>` returns 404, and that supabase-js reads are blocked by RLS.
6. Sign out mid-task and check the session-expired message.
7. Use a bad bucket region on purpose and expect a `storage_config` error with no secrets in the logs.
8. Clean up the test objects and rows.
